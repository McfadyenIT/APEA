1 · Upload your BlazeMeter recording

LT Metrics works entirely from your recording — JMeter .jmx, Taurus/BlazeMeter .yaml/.yml, or .har. It reads the journey, auto-correlates dynamic values, and tells you exactly what data to upload.

1b · Or — crawl & record with a headless browser (no recording needed)

No recording to upload? Give LT Metrics a target URL above and it drives a real headless browser (Playwright) through the site itself — home page, search, login (if you give credentials below), add a product to cart, view the cart — and captures the actual requests it makes along the way, the same way an uploaded recording would. It stops at add-to-cart: checkout and payment forms vary too much across sites to drive blindly, so that part still benefits from an uploaded recording. Requires Playwright on the server (pip install playwright && playwright install chromium) — otherwise this just tells you so instead of failing silently.

LT Metrics reads the plan and recommends the test types it describes — with users, duration, ramp-up, think time, SLA, objectives and scenarios — then pre-fills the fields below (all editable). It does not auto-run anything. No API key needed.

Payment token & CAPTCHA (rarely needed)
{{column}} reads that column from each user’s own row. Add a default after a pipe — {{card_cvv|123}} — for a value that is the same for the whole pool, and you can drop the column entirely. A placeholder with no default and no value stops the run rather than paying by some other method.
💳 Real-browser payment track (Playwright) — drive real card iframes

Runs a small pool of REAL browsers alongside the load test to complete a hosted card payment (Stripe / CyberSource) that HTTP replay can't. Requires Playwright (run setup-browser-track.bat once). Leave Browser VUs at 0 to keep it off — the normal HTTP load test is unchanged.

🧪 Intelligent Test Data Generator

Generates realistic, validated data for the selected test — customers, products (distributed so users don't all buy one SKU), addresses, payments and search terms — sized from the plan. The result becomes this run's data set, and throughput / test type / users are set for you. Analyze a recording first (optionally upload a test plan above).

🤖 AI Auto-heal 

      
When a run fails, Claude reads the actual failures, fixes the script
        (correlation, headers, REST prefix, payment method, address fields…) and regenerates
        it. Broken-script failures are re-run automatically; a timed run that produced traffic
        is healed for the next run so it still stops at its duration.

      

    


    

      
Where the time went

      
Every call in the run, grouped by the stage of the journey
        it belongs to. Stages appear in the order the run first reached them —
        whatever stages your recording actually has. Click a stage to see the
        calls inside it.

      
Time is what a stage cost in total. Spans is
        how long it was in play from first call to last. With users running at
        the same time these differ a lot, and reading one as the other is the
        easiest way to misread a load test. Transaction timers are left out:
        one contains the calls inside it, so counting it would add the same
        milliseconds twice.
